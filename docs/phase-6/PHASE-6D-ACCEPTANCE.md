## Architecture decisions

### Why a partial unique index rather than a DB lock

A `SELECT ... FOR UPDATE` advisory lock would require raw SQL and knowledge of
the exact table name inside a `$transaction`. A partial unique index on
`(trackId) WHERE kind='MUSIC_TRACK'` achieves the same serialization guarantee
at the DB level with zero raw SQL in the service code. The P2002 error from
Prisma's `create` is the concurrency signal; the catch converts it to CONFLICT.

### Why cue cleanup on failure (not Phase 6C behaviour)

Phase 6C left orphaned unmaterialised cues after Lyria failures. With the
partial unique index, those orphans would permanently block retries. Phase 6D
adds best-effort `audioCue.delete` in the failure path so the track is unlocked
and subsequent requests can proceed. The delete is wrapped in a no-throw
try-catch so cleanup failures never mask the original provider error.

### Why router ownership checks are in the router, not the service

The service (`generateMusicForVersion`) is designed to be called internally with
trusted inputs. Ownership validation belongs at the API boundary (the router),
where the caller's identity is known. This keeps the service testable without
user context and consistent with the pattern used by all other Creative routers.

### Why output/service.ts is unchanged

The current output pipeline is purely visual. Integrating materialised music
`AudioCue` rows into the FFmpeg/assembly render is Phase 6E scope. Phase 6D
ensures the infrastructure (router, materialised assets, unlocked tracks) is
ready for that integration without premature coupling.
